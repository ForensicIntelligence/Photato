# Contributing to the native Swift fork

This is an independent macOS port of [PhotoCraft](https://github.com/storytold/photocraft). The goal is Photoshop 2026 feature parity in a native Swift application; the existing Rust app is the behavioral source and an intermediate parity milestone. The current app is a development preview. Read [STATUS](docs/STATUS.md), [the porting plan](docs/PORTING_PLAN.md), and [the command checklist](docs/COMMAND_PARITY.csv) before choosing work.

Build with Xcode 27 / Swift 6.4 using `./scripts/test.sh` and `./scripts/build-app.sh`. The deployment target is macOS 14; Apple AI is optional and separately gated. Build scripts run from this directory, including when it is nested inside a fork of the upstream repository. API integration tests bind ephemeral IPv4 loopback ports and require local networking permission; an execution sandbox that forbids listeners will fail those tests. Native sheet lifecycle tests also require host AppKit access; a restricted sandbox may prevent the sheets from attaching. Preserve that failed attempt and rerun with permitted loopback access rather than skipping the integration coverage.

For native Xcode development, open `Photato.xcodeproj`, choose **Photato / My Mac**, and run with Command-R. The shared scheme archives a universal Release app. Local signing is ad-hoc; distribution still needs the release signing configuration. The included project builds without XcodeGen. Maintain build configuration in `project.yml` and regenerate with XcodeGen 2.45.2 when changing settings/resources; synchronized source groups discover new Swift files automatically. Keep the generated project and specification together. Run regression tests with `./scripts/test.sh`; the main app scheme has no XCTest targets. Keep Xcode Derived Data/archives outside Desktop because File Provider metadata can interfere with signing.

Keep the application and editing engine in Swift with native Apple UI/imaging frameworks. Keep commands transactional and undoable; preserve layer editability and metadata; report unsupported formats explicitly. Reproduce a behavior with a deterministic test or independent reference file, implement it, and verify the user-facing workflow. Do not treat a menu entry or a self-generated file round trip as proof of Photoshop parity.

API coverage is a required part of every new or expanded feature. Include its API operations/state, schemas, capability discovery, documentation and relevant regression tests in the same increment. Desktop and API paths must share the native Swift implementation and matching document/history behavior. Record API impact for presentation changes as well. A menu inventory entry alone is not an implementation. See [the API completion requirement](docs/AUTOMATION_API.md#feature-completion-requirement).

Maintain both the Photato API and an Adobe Photoshop API v2 GA-compatible interface in Firefly Services terminology. Both use the same native Swift engine. New capabilities require Photato API support plus Adobe-compatible coverage wherever Adobe defines the operation, with documentation and tests for both. Preserve existing Photato clients and each interface’s versioned contract, including Adobe’s asynchronous job behavior. Add conformance tests and track endpoint-level support; keep Photato-only extensions separate. The current proprietary /v1 preview is not Adobe-compatible. Read [the compatibility plan](docs/ADOBE_API_COMPATIBILITY.json) before extending the API.

For pull requests, describe the editing problem, resulting behavior, tests, and remaining limitations. Update the status and command checklist when measurable functionality changes. Keep unrelated work and upstream Rust changes separate. Existing licenses and attribution notices must remain. Contributions are offered under MIT OR Apache-2.0, matching the fork, unless explicitly agreed otherwise. Identify the source and license of any borrowed code, fixtures or assets.

Do not include private documents, downloaded model weights, credentials, build caches, app bundles or downloaded reference corpora in a source PR. Bundled small test fixtures need provenance and redistribution terms. Keep user projects out of bug reports; prefer a minimal reproducible fixture that can be shared.

Photato will be released as free and open-source software under MIT OR Apache-2.0. Contributions of code, bug reports, tests, documentation and accessibility improvements are welcome. The app contains no tipping or purchase system.

## Development record

The maintainer requires documentation of every development step, starting with the original source audit. [DEVLOG](docs/DEVLOG.md) is the narrative record, with an oldest-first index and stable step IDs. [DEVELOPMENT_HISTORY.json](docs/DEVELOPMENT_HISTORY.json) indexes the surviving evidence. These records are part of completing the work, not an optional release cleanup.

[The development diary](docs/DEVELOPMENT_DIARY.md) provides the readable chronological account and links every recorded milestone to DEVLOG. Keep its index and material narrative current at completed checkpoints. Detailed notes must still be saved as work proceeds, including failed attempts and work that is later removed.

For every meaningful investigation, design decision, implementation change, experiment and validation step, record:

1. Date and stable step ID; include time and time zone when known. Describe the request or defect and the intended scope.
2. Sources examined, behavior observed and affected files/modules. Identify external references, source translations and fixture provenance.
3. What changed and why. Preserve rejected approaches, failed attempts, discovered defects and their repairs, including documentation-only work.
   Explicitly record additions, modifications, deletions, renames, rollbacks and replacements across code, tests, assets, configuration, documentation and APIs. Name affected paths or modules, explain the before/after behavior, and identify the replacement when something is removed. Group related edits when useful, but do not omit removals or unverified work.
4. Exact test/build/diagnostic commands, unique log paths, outcomes, failure/skip counts and relevant measurements. Distinguish focused/full tests, current/historical results, native round trips and independent Photoshop comparisons.
5. Live UI actions and their observed outcome, including cancellation/undo and cleanup of disposable documents. Record the app/platform/binary actually checked. Never label an offscreen snapshot as a live interaction test.
6. Remaining gaps, uncertainty, blockers and next steps. Update the current status, command matrix, plan and relevant reference manifests when their facts change.

Add notes as work proceeds and finish the entry before ending a work session. Extend a current entry with clearly ordered substeps; allocate the next `dev-step-NNN` ID for a new milestone. Keep newest detailed entries first and the navigation table oldest first. Preserve prior accounts and corrections: label retrospective additions with their reconstruction date and supporting evidence rather than implying they were recorded at implementation time.

Use distinct paths such as `artifacts/runs/<UTC-date-time>-<step>-<attempt>/` for each test, build or experiment. Record failed output before applying a repair and retain the passing rerun separately. If an existing script writes a fixed filename, copy that output to a unique run directory before rerunning it. Generic names such as `full-tests.log`, `verification.json`, and `photato-release-verification.json` are rolling current summaries. They must not be the sole evidence for a historical claim. Source hashes, package hashes and dated manifests bind release evidence to the build actually tested; filesystem modification times alone do not establish development chronology.

Refresh the inventory with `python3 scripts/audit-development-history.py`, then run `python3 scripts/audit-development-history.py --check`. The script preserves changed prior inventories by content hash. Check missing references and explain anything that cannot be recovered. It validates documentation and current evidence hashes; it does not run application tests or prove complete historical coverage. For documentation-only changes, verify links/inventory and confirm application source/package hashes remain unchanged instead of rerunning unrelated native tests.

The original Rust snapshot has no preserved upstream Git history, and the native subtree is currently untracked in the enclosing Desktop repository. Do not invent a base commit or treat these logs as a replacement for future version history. Before publication, follow [the fork/release plan](docs/OPEN_SOURCE_RELEASE.md), and curate local evidence so private documents, credentials and machine-specific material are not published inadvertently.
